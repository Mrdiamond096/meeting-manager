# Review: Cursor — `docs/AI-thinks/cursor/`

ผู้รีวิว: Claude · วันที่: 2026-11-12
ขอบเขต: อ่านครบ `ARCHITECTURE_PROPOSAL.md` (หน้า index) และทั้ง 23 ไฟล์ใน `architecture-proposal/` (รวม ~1,900 บรรทัดทั้งโฟลเดอร์ docs/AI-thinks)

## สรุปสั้น

**ข้อเสนอของ Cursor ไม่ใช่มุมมองอิสระ** — เป็นเนื้อหาของ Claude ที่ถูกแตกเป็นไฟล์ย่อย พร้อมสารบัญ เมื่อเทียบกับ `docs/AI-thinks/claude/ARCHITECTURE_PROPOSAL.md` พบว่า ~84% ของบรรทัด (363 จาก 435 บรรทัดไม่ซ้ำ) เหมือนกันทุกตัวอักษร ส่วนที่เหลือส่วนใหญ่เป็นหัวข้อ (`# 1. ...`) และจุดที่ผมแก้ตอนเขียนฉบับ docs/claude ใหม่ ดังนั้นสำหรับการเปรียบเทียบข้าม AI ฉบับนี้ **ไม่เพิ่มข้อมูลใหม่** นอกจากรูปแบบการจัดเอกสาร

## หลักฐานว่าเป็นสำเนา

- หัวเรื่อง, legend (`[REQ]/[ASM]/[REC]`), แนวทาง Approach A/B/C, ตารางเทียบ, stack, ADR 001–013, edge-case matrix เหมือนกัน
- มี **ตำหนิเฉพาะตัวร่วมกัน** ที่ไม่ใช่ความบังเอิญ เช่น ER diagram มีเส้น `USERS ||--o{ FEEDBACK` ทั้งที่ `feedback.author` เป็นแค่ข้อความ, endpoint `/meta` ซ้ำซ้อนกับ shared constants, และ error code ที่บอก `400/422` พร้อมกันในตาราง
- ข้อความ "Would ask the hiring team…" ต่างจากฉบับ docs/claude เพียงเล็กน้อยตรงกับฉบับแรกที่ผมเขียนที่ root (ซึ่งตอนนี้ไม่อยู่แล้ว)
- ไฟล์ index ยังใช้ชื่อเรื่องเดียวกับของผมและบอกว่า "has been modularized and split" ซึ่งสื่อว่าเป็นการแตกไฟล์ ไม่ใช่การเขียนขึ้นใหม่

(ผมไม่ทราบกลไกว่า Cursor ได้เนื้อหานี้มาอย่างไร — อาจอ่านไฟล์ของ Claude ที่ root ก่อนมันหาย ข้อสรุปนี้อิงจากเนื้อหาเท่านั้น)

## ข้อดี

1. **โครงสร้างไฟล์อ่านและ review ง่าย**: แยกตามหัวข้อ 01–23, มีสารบัญจัดกลุ่ม 5 ส่วน (Requirements / Architecture / Design / Ops / Conclusions) ลิงก์ข้ามไฟล์ได้ เหมาะกับการ review ทีละหัวข้อหรือคอมเมนต์ใน PR
2. **ไฟล์เล็กและโฟกัส** แก้เฉพาะส่วนได้โดยไม่กระทบทั้งเอกสาร diff เล็ก (เช่น 21 final recommendation มี 6 บรรทัด)
3. **เนื้อหาแข็งแรงตามที่ Claude เสนอ**: ครบ 22 หัวข้อตาม Master Prompt, ครอบคลุม wireframe ด้วย superset model, ตัดสินใจ stack ที่เล็กและสอดคล้อง, มี Mermaid diagram 5 แบบ, plan 7 วันพร้อม gate และลำดับตัดงาน, edge-case matrix
4. **แยก edge-case matrix เป็นไฟล์เฉพาะ (23)** เปิดดูเป็นเช็กลิสต์ได้สะดวก

## ข้อเสีย / ความเสี่ยง

1. **ไม่ใช่การวิเคราะห์อิสระ** — ผลคือไม่มีตัวเลือก/ข้อโต้แย้ง/การตีความใหม่ให้เทียบ ถ้านับเป็น "หนึ่งเสียง" ในการเปรียบเทียบจะทำให้ความเห็นของ Claude ถูกนับซ้ำและบิดเบือนการสรุปว่าแนวทาง B+Postgres+Render "ได้รับฉันทามติ"
2. **ไม่ระบุที่มา**: ไม่มีข้อความบอกว่าเนื้อหามาจากเอกสารอื่น ผู้อ่านที่เปิดโฟลเดอร์ cursor อย่างเดียวอาจเข้าใจว่าเป็นงานเขียนของ Cursor
3. **สืบทอดข้อบกพร่องของต้นฉบับทุกอย่าง** (ดูหลักฐานข้างบน) และไม่แก้ไขแม้แต่ข้อเดียว เช่น `strict` on write ขัดกับ "strip unknown keys" ในเอกสารเดียวกัน, route `/candidates/:id` เป็น alias ของ `/meetings/:id` แต่ไม่ได้กำหนดว่าใช้อันไหน
4. **จุดอ่อนเชิงเนื้อหาที่ติดมาจาก Claude** (ไม่ใช่ความผิดของ Cursor แต่ยังอยู่ในเอกสาร):
   - ประมาณเวลาเป็นวันโดยไม่มีช่วงความมั่นใจต่อรายการ และแผนแน่นเมื่อรวม wireframe + auth + deploy
   - ครอบคลุมความถูกต้องเชิงลึกน้อยกว่า Codex (DST, pagination snapshot, delete ด้วย version)
   - Auth/Playwright/OpenAPI อาจเกินสำหรับ 1 สัปดาห์ถ้ามีสิ่งผิดพลาด
5. **การแตกไฟล์ไม่มีแม้ index ของ diagram/ตาราง** และเพิ่มภาระ: ต้องเปิด 23 ไฟล์เพื่ออ่านครบ ไม่เหมาะกับการส่งให้คนอื่น review ทีเดียว (ไม่มีไฟล์รวม) และ anchor ภายในเอกสาร (เช่น "See 13") ไม่ลิงก์ไปไฟล์
6. **เลขหัวข้อเพี้ยน**: เอกสารมี 22 หัวข้อ แต่ไฟล์ edge case เป็นไฟล์ที่ 23 และ index ระบุว่า "22. ADR" ตามด้วย "23." ขณะที่ Master Prompt กำหนดโครงสร้าง 22 ข้อ (เป็นภาคผนวกในต้นฉบับ)

## ข้อเสนอแนะ

- **อย่านับ Cursor เป็นข้อเสนอแยกในการตัดสินใจ** ให้ถือว่ามี 2 มุมมองอิสระ คือ Claude และ Codex
- ถ้าอยากได้มุมมองอิสระจาก Cursor จริง ให้รัน prompt เดิมใหม่ในโฟลเดอร์ที่ไม่มีข้อเสนอของ Claude อยู่ (หรือสั่งให้ไม่อ่านโฟลเดอร์อื่น)
- รูปแบบการแตกไฟล์เป็นข้อเสนอที่ดีสำหรับเอกสารสุดท้ายใน repo (เช่น `docs/architecture/` + ADR แยกไฟล์) — นำไปใช้ได้โดยไม่เกี่ยวกับผู้เขียน
